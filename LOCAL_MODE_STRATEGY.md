# Практическая стратегия: вынос локального режима как отдельное направление

## Краткая рекомендация

Не делайте это как `branch` и не превращайте это в "fork" в смысле копию всего проекта.
Лучший вариант для вашего случая — отдельное направление с общей библиотекой/ядром, которое оба режима используют:

- `core` / `shared` — общие модули и логика
- `bot` — Telegram-бот
- `obs-local` — локальный запуск для OBS/трансляций

Так вы сохраните:
- общую логику конвертации
- совместимость с текущими библиотеками
- независимую разработку локального пайплайна
- минимальные риски для боевого бота

---

## Почему это правильнее, чем fork или branch

У вас уже есть признаки, что логика разделена на слои:

- `converter_engine.py` — общая конвертация
- `yandex_disk.py` — общий клиент Яндекс.Диска
- `sermon_detector.py` — разбор речи/сегментов
- `utils.py` — общие функции
- `obs_local.py` — локальный сценарий с ручным выбором диапазона и файлов
- `bot.py` / `handlers.py` — Telegram-оркестрация

Это значит, что локальный режим — это не отдельная версия продукта, а отдельный сценарий использования. Он использует те же библиотеки и функции, но запускается иначе.

Поэтому правильнее:

1. выделить общее ядро;
2. оставить код бота как отдельный слой;
3. локальный режим сделать отдельным направлением/подпроектом, который зависит от общего ядра.

## Рекомендуемая модель

### Вариант A — самый безопасный для текущего проекта: один репозиторий с разделением по папкам

Это лучший вариант, если вы хотите минимально ломать текущую структуру.

```text
pptx2png/
├── core/
│   ├── pptx2png_core/
│   │   ├── __init__.py
│   │   ├── converter_engine.py
│   │   ├── sermon_detector.py
│   │   ├── utils.py
│   │   ├── yandex_disk.py
│   │   └── ...
│   └── pyproject.toml
├── bot/
│   ├── bot.py
│   ├── handlers.py
│   ├── yandex_flow.py
│   ├── yandex_state.py
│   ├── settings.ini
│   └── requirements.txt
├── obs_local/
│   ├── obs_local.py
│   ├── run_obs_local.py
│   ├── settings.ini
│   └── requirements.txt
├── .github/
│   └── workflows/
├── README.md
├── .gitignore
└── pyproject.toml
```

Плюсы:
- не надо мигрировать весь проект в новый repo
- легче управлять совместимостью
- локальный режим развивается независимо
- общие модули можно импортировать как пакет

Минусы:
- нужно аккуратно настроить импорты
- нужно разделить окружения и config

### Вариант B — отдельный репозиторий для core и отдельный для локального режима

Если проект растёт и локальный режим становится серьёзным продуктом:

```text
pptx2png-core/
├── pptx2png_core/
├── pyproject.toml
└── README.md

pptx2png-bot/
├── bot/
├── requirements.txt
├── .github/workflows/
└── README.md

pptx2png-obs-local/
├── obs_local/
├── requirements.txt
├── README.md
└── .github/workflows/
```

Плюсы:
- чистая архитектура
- более сильная изоляция
- проще поддерживать разные релизы

Минусы:
- сложнее с синхронизацией библиотек
- больше операционных расходов

## Что я рекомендую именно вам

Если вы хотите минимальный риск и быстрое внедрение — сначала вариант A.

То есть:

1. оставить текущий репозиторий как основной проект
2. выделить `core/` и сделать общий пакет
3. перевести `obs_local.py` и `bot` в автономные entry points
4. позже, если станет действительно отдельной линией, можно вынести в отдельный repo

Это даёт “плавный переход”, без риска сломать боевой бот.

## Практический план по GitHub

### Шаг 1. Сначала не менять ветки, а разнести ответственность

Создайте в проекте такие папки:

- `core/`
- `bot/`
- `obs_local/`

Или, если хотите меньше менять структуру: создайте пакеты внутри текущего repo:

- `pptx2png_core/`
- `bot/`
- `obs_local/`

### Шаг 2. Сделать shared package

Вытащите в `pptx2png_core` всё, что реально используется и ботом, и локальным режимом:

- `converter_engine.py`
- `sermon_detector.py`
- `utils.py`
- `yandex_disk.py`
- `structure.py` (если это полезно в обоих режимах)

Оставьте только точку входа в боте и локальном режиме:

- `bot.py` — для Telegram
- `obs_local.py` — для локального запуска

### Шаг 3. Настроить GitHub Actions

Создайте рабочие процессы:

- `ci.yml` — тесты и lint
- `bot-deploy.yml` — деплой бота
- `obs-local-deploy.yml` — для локального режима, если он будет запускаться отдельно

Базовый принцип:

- `main` — основная ветка общего ядра
- `test` — проверка стабильности
- `prod` — только боевой бот
- локальный режим может жить в том же репозитории, но в отдельных директориях/обозначенных этапах

### Шаг 4. Сделать три уровня релизов

- `core` release — общие библиотеки
- `bot` release — боевая версия бота
- `obs-local` release — локальный сценарий для машинистов/OBS

То есть не “один проект = один релиз”, а “одна база + несколько приложений поверх неё”.

## Практический план на локальной машине

### Шаг 1. Создать виртуальное окружение

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### Шаг 2. Установить общее ядро в editable mode

Если вынесли в отдельный каталог:

```bash
cd /path/to/pptx2png-core
pip install -e .
```

Если всё в одном repo:

```bash
pip install -e ./core
```

Это важно: вы будете работать с актуальным кодом без копирования.

### Шаг 3. Установить зависимости для бота и локального сценария

```bash
pip install -r bot/requirements.txt
pip install -r obs_local/requirements.txt
```

или, если это один repo с общим пакетом:

```bash
pip install -r requirements.txt
```

### Шаг 4. Проверить импорты

Вместо:

```python
from converter_engine import convert_all_pngs
```

лучше делать:

```python
from pptx2png_core.converter_engine import convert_all_pngs
```

или при монорепозитории:

```python
from core.pptx2png_core.converter_engine import convert_all_pngs
```

### Шаг 5. Разделить конфиги

`bot` и `obs_local` должны иметь свои config-файлы, даже если они используют общие модули.

Например:

```text
config/
├── bot.ini
├── obs_local.ini
└── secrets.ini
```

или:

```text
bot/settings.ini
obs_local/settings.ini
```

Главное: не мусорить секретные данные в общем ядре.

### Шаг 6. Запускать отдельными entry points

```bash
python bot/bot.py
```

```bash
python obs_local/obs_local.py
```

или через CLI:

```bash
python -m bot
python -m obs_local
```

## Как переводить код без риска

### Этап 1 — безопасный рефакторинг

- оставить текущий код как есть
- создать `pptx2png_core`
- перенести туда общие модули
- оставить временные импорты совместимости

Пример совместимости:

```python
# temporary compatibility layer
from pptx2png_core.converter_engine import convert_all_pngs
```

### Этап 2 — переключить bot

Поменять импорт в `handlers.py`, `bot.py`, `yandex_flow.py` на новый пакет.

### Этап 3 — перевести obs_local

Поменять импорты в `obs_local.py` на тот же общий пакет.

### Этап 4 — удалить дубликаты

Когда оба режима работают, убрать старые локальные копии и оставить только чистую общую API.

---

## Что важно не делать

- Не делать "copy-paste fork" без проверки общих функций
- Не держать одну и ту же библиотеку в двух местах
- Не хранить токены и конфиги внутри `core`
- Не ставить локальный режим как полноценную ветку без архитектурного разделения
- Не смешивать `bot` и `obs_local` в одной логике запуска, если они реально разные

## Рекомендация по GitHub workflow

### Минимальный вариант

- `main` — общая разработка
- `test` — интеграционные проверки
- `prod` — боевой бот
- локальный режим остаётся в той же ветке, но в отдельной папке

### Более зрелый вариант

- `core` repo или package
- `bot` repo or module
- `obs-local` repo or module

Если локальный режим станет более “клиентским инструментом”, именно тогда полезен отдельный repo.

---

## Итоговая схема

Мой практический совет:

1. Не branch
2. Не полный fork
3. Сделать разделение на `core + bot + obs_local`
4. На GitHub — либо один репозиторий с папками, либо три репозитория, если проект станет большим
5. На локальной машине — использовать `pip install -e` для общего пакета
6. Разделить `config`, `env`, `entry points`, но оставить общий код в одном месте

Так вы получите:
- сохранённую связь с основными библиотеками
- независимое развитие локального сценария
- меньше риска для работающего бота
- понятную архитектуру для будущего роста

---

## Рекомендуемое следующее действие

Сначала сделать это в текущем репозитории так:

1. создать папку `core/`;
2. перенести общие модули туда;
3. оставить `bot/` и `obs_local/` как entry points;
4. проверить, что бот работает без изменения бизнес-логики;
5. только потом решать, переносить ли это в отдельный GitHub repo.

Это самый безопасный путь.
